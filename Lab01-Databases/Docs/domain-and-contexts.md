# Предметна область та межі контекстів — «Система управління відеопрокатом»

> Лабораторна робота № 01. Крок 1 і Крок 2 методики.

## 1. Опис домену

Система обслуговує **міську мережу відеопрокату**. Оператори ведуть каталог фільмів
(режисери, жанри, фізичні диски на полицях), оформлюють клієнтам оренду фільмів на
визначений термін, приймають повернення та нараховують пеню за прострочення.
Клієнти додатково пишуть відгуки на фільми, обговорюють їх і складають власні
підбірки для перегляду.

Три групи даних живуть за різними правилами: **каталог** змінюється рідко й має
строгі зв'язки, **оренда** — транзакційний процес зі станами й грошима, **відгуки** —
слабко структурований контент із вкладеними обговореннями. Саме тому систему
розділено на три незалежні контексти, кожен зі власною базою даних.

## 2. Три обмежені контексти (Bounded Contexts)

| Проєкт | Контекст | Технологія персистентності | Чому саме ця технологія |
|---|---|---|---|
| **№1** | **Оренда** (Rentals) | SQL Server + **ADO.NET & Dapper** | Оренда — транзакційний процес (оформлення → підтвердження → видача дисків → повернення). Потрібні збережувані процедури, явні транзакції, перевірка допустимості переходів статусів і контроль цілісності «на рівні бази». |
| **№2** | **Каталог** (Catalog) | SQL Server + **EF Core (Code First)** | Каталог — багато сутностей і всі три типи зв'язків (1:1, 1:N, M:N із власним полем). Зручно показати Fluent API, міграції та seed-дані. |
| **№3** | **Відгуки** (Reviews) | **MongoDB** | Відгуки, коментарі й обговорення мають динамічну структуру: різні клієнти залишають різні набори полів (фото, теги, детальні оцінки, відео-відгук). Природно лягає на документи з піддокументами. |

### Розподіл сутностей (кожна належить рівно одному контексту)

**Проєкт №1 — `VideoRentalRentalsDb`** (власник даних про оренду):
- `Customers` — клієнти відеопрокату *(власна сутність контексту)*
- `Rentals` — оренда, коренева сутність агрегату
- `RentalDetails` — деталі оренди (1:1)
- `RentalItems` — позиції оренди (M:N між `Rentals` і `Movies`)
- `RentalStatusHistory` — журнал переходів статусів
- `LateFeePayments` — оплати пені
- `Movies` — **локальна копія довідника** з Каталогу (не власна сутність!)

**Проєкт №2 — `VideoRentalCatalogDb`** (власник даних про фільми):
- `Directors` — режисери
- `Movies` — фільми, **власник ідентифікатора фільму в усій системі**
- `MovieDetails` — опис фільму (1:1)
- `DiscCopies` — фізичні диски (1:N)
- `Genres` — жанри
- `MovieGenres` — проміжна сутність M:N із власним полем `AddedAt`

**Проєкт №3 — `VideoRentalReviewsDb`** (власник контенту клієнтів):
- `reviews` — відгуки
- `discussions` — обговорення
- `watchlists` — підбірки фільмів
- `customerProfiles` — профілі клієнтів у контексті відгуків

### Правило належності

`Movie` існує в усіх трьох контекстах, але **власник один — Каталог (Проєкт №2)**.
Контекст Оренди зберігає локальну копію довідника (`dbo.Movies`) і знімки полів у
позиціях, контекст Відгуків — лише `movieId` і денормалізовану назву.
Аналогічно `Customer` належить контексту Оренди, а `customerProfiles` у MongoDB — це
окрема сутність контексту Відгуків, що лише посилається на `Customers.Id`.

## 3. Агрегати й межі даних (Крок 2)

| Контекст | Агрегат | Склад | Життєвий цикл |
|---|---|---|---|
| Оренда | **Rental** | `Rentals` + `RentalDetails` + `RentalItems` + `RentalStatusHistory` | Позиції не існують без оренди й змінюються лише через неї. Видалення оренди каскадно видаляє позиції, деталі та історію. |
| Оренда | **Customer** | `Customers` + `LateFeePayments` (через `Rentals`) | Клієнта **не** видаляємо каскадно: історія оренд має зберігатися (soft delete `IsDeleted`). |
| Каталог | **Movie** | `Movies` + `MovieDetails` + `DiscCopies` + `MovieGenres` | Опис і диски не існують без фільму (каскад). Жанр — довідник, живе окремо. |
| Каталог | **Director** | `Directors` | Режисера не можна видалити, поки є його фільми (без каскаду). |
| Відгуки | **Review** | документ `reviews` + вбудовані `comments[]` | Коментарі живуть разом із відгуком. Довга ветка винесена в `discussions` за посиланням. |
| Відгуки | **Discussion** | документ `discussions` + `messages[]` | Необмежено зростає, тому окремий документ, а не вбудовування у відгук. |

## 4. Міжконтекстні посилання — без FOREIGN KEY

```
VideoRentalCatalogDb.Movies.Id  (ВЛАСНИК ідентифікатора фільму)
        │
        ├─ ─ ─ ►  VideoRentalRentalsDb.Movies.Id        (локальна копія довідника)
        │             └─ ─ ─ ► VideoRentalRentalsDb.RentalItems.MovieId (+ знімки полів)
        │
        └─ ─ ─ ►  VideoRentalReviewsDb.reviews.movieId  (+ денормалізована movieTitle)
                   VideoRentalReviewsDb.discussions.movieId
                   VideoRentalReviewsDb.watchlists.items[].movieId

VideoRentalRentalsDb.Customers.Id  (ВЛАСНИК ідентифікатора клієнта)
        └─ ─ ─ ►  VideoRentalReviewsDb.reviews.author.customerId
                   VideoRentalReviewsDb.customerProfiles.customerId
```

`─ ─ ─ ►` — **логічне** посилання за ідентифікатором: звичайний стовпець без
обмеження. Цілісність за потреби перевіряє прикладний код.
`─────►` (суцільна лінія) — справжній `FOREIGN KEY`, існує **лише в межах однієї
бази**.

Перевірка: `SELECT * FROM sys.foreign_keys` у кожній SQL-базі не показує посилань
за межі цієї бази (див. `verify.sql`, блок 1).

## 5. Таблиця політики дублювання даних

> Крок 2 методики. Мінімум один рядок на кожну пару контекстів, що взаємодіють.

| № | Поле | Де зберігається | Джерело (власник даних) | Політика узгодженості |
|---|---|---|---|---|
| 1 | `RentalItems.MovieTitle`, `RentalItems.MovieDirector`, `RentalItems.DailyRate` | `VideoRentalRentalsDb` (Проєкт №1) | `Movies` у `VideoRentalCatalogDb` (Проєкт №2) | **Знімок на момент оформлення оренди — свідомо НЕ оновлюється.** Тариф і назва, за якими оформлено оренду, мають залишитися незмінними, навіть якщо каталог їх змінить. Так само `OrderItem` в eShop зберігає `ProductName` і `UnitPrice`. |
| 2 | `Movies.Title`, `Movies.Director`, `Movies.Barcode`, `Movies.DailyRate` (локальна копія довідника) | `VideoRentalRentalsDb` (Проєкт №1) | `Movies` у `VideoRentalCatalogDb` (Проєкт №2) | **Копія для читання — оновлюється подіями з Каталогу** (`MovieUpdated`, `MoviePriceChanged`). Потрібна, щоб форма оформлення оренди не робила синхронний виклик до Каталогу на кожне читання. Механізм подій — Лаб. 08; до того копія синхронізується `seed`/скриптом (`MERGE` у `seed.sql`). |
| 3 | `Movies.DiscsAvailable` | `VideoRentalRentalsDb` (Проєкт №1) | **Власник — Проєкт №1** (а не Каталог) | **Не дублювання, а власні дані контексту Оренди.** Залишок доступних для оренди дисків змінюють саме операції оренди/повернення, тому `seed.sql` його не перетирає (`MERGE ... WHEN MATCHED` оновлює все, крім цього поля). `Catalog.Movies.AvailableDiscs` — окреме поле з іншим змістом: скільки дисків узагалі є на балансі. |
| 4 | `reviews.movieTitle`, `discussions.movieTitle`, `watchlists.items[].movieTitle` | `VideoRentalReviewsDb` (Проєкт №3) | `Movies` у `VideoRentalCatalogDb` (Проєкт №2) | **Копія для читання — оновлюється подіями з Каталогу.** Денормалізація дає змогу показати список відгуків без жодного звернення до Каталогу. |
| 5 | `reviews.author.displayName`, `watchlists.owner.displayName`, `customerProfiles.displayName` | `VideoRentalReviewsDb` (Проєкт №3) | `Customers` у `VideoRentalRentalsDb` (Проєкт №1) | **Знімок імені на момент публікації — НЕ оновлюється.** Відгук підписаний тим іменем, під яким його опублікували. Відгук може бути й анонімним — тоді `customerId` відсутній узагалі. |
| 6 | `RentalStatusHistory.ToStatus` | `VideoRentalRentalsDb` | **Власні дані контексту** | Не дублювання: журнал подій агрегату Rental. |

### Чому дублювання допустиме і що ми втрачаємо

Дублювання **роз'єднує сервіси**: сервіс Оренди читає назву фільму зі своєї бази й не
падає, коли Каталог недоступний. Натомість ми втрачаємо строгу узгодженість —
між зміною в Каталозі й оновленням копії є вікно, протягом якого дані розходяться
(**eventual consistency**).

**Неприпустимий випадок (dual write)**, якого в цьому проєкті немає: дві копії поля,
які **незалежно редагуються** в різних сервісах без визначеного власника. Тому для
кожного рядка таблиці вище вказано рівно одного власника даних.

## 6. Обґрунтування вибору первинних ключів

| Таблиця | PK | Обґрунтування |
|---|---|---|
| `Customers`, `Rentals`, `RentalStatusHistory`, `LateFeePayments` | `BIGINT IDENTITY(1,1)` | Вставка йде **лише з одного джерела** — сервісу Оренди. Послідовні значення дають компактні, не фрагментовані індекси. GUID тут був би зайвими 8 байтами в кожному індексі. |
| `VideoRentalRentalsDb.Movies` | `BIGINT` **без** `IDENTITY` | Id **приходить із Каталогу** — це той самий ідентифікатор, що й `VideoRentalCatalogDb.Movies.Id`. Генерувати його тут заборонено. |
| `RentalDetails` | `BIGINT` = FK на `Rentals` | Зв'язок 1:1: PK залежної таблиці є водночас зовнішнім ключем, тому фізично неможливо мати два рядки деталей на одну оренду. |
| `RentalItems`, `MovieGenres` | складений `(RentalId, MovieId)` / `(MovieId, GenreId)` | M:N: складений ключ сам гарантує, що пара не повториться. |
| `VideoRentalCatalogDb.Movies` | `BIGINT IDENTITY(1,1)` | Власник ідентифікатора фільму; вставка лише з сервісу Каталогу. |
| `Directors`, `Genres` | `INT IDENTITY(1,1)` | Невеликі довідники, `BIGINT` не потрібен. |
| `reviews`, `discussions`, … | `ObjectId` | Стандарт MongoDB: генерується на клієнті, містить часову компоненту, не потребує звернення до сервера. |

## 7. Аудит, м'яке видалення та конкурентність (Крок 6)

- **Аудитні колонки** `CreatedAt`, `CreatedBy`, `UpdatedAt`, `UpdatedBy` — у
  `Customers`, `Rentals`, `Directors`, `Movies` (обох баз).
- **М'яке видалення** `IsDeleted BIT` — у `Customers`, `Rentals`, `Directors`, `Movies`,
  `Genres`. Фільтровані індекси (`WHERE IsDeleted = 0`) обслуговують лише «живі»
  записи й тому менші за розміром.
- **Оптимістична конкурентність** `ROWVERSION` — у `Customers`, `Rentals`, `Movies`
  (обох баз). Обґрунтування вибору: конкурентні записи одного рядка тут **рідкі**
  (двоє операторів нечасто редагують ту саму оренду), тому `optimistic` дешевша
  за постійні блокування. Конфлікт виявляється під час запису і повертається
  клієнту як `409 Conflict`.
- **Песимістичне блокування** застосовано точково — у збережуваних процедурах
  (`WITH (UPDLOCK)` при читанні статусу перед його зміною). Тут конфлікт потрібно
  **запобігти**, а не виявити: два паралельні підтвердження оренди не повинні
  обидва зменшити залишок дисків.
- **Компроміс рівня ізоляції:** усі бізнес-транзакції працюють на
  `READ COMMITTED` (значення за замовчуванням SQL Server). Вищий рівень
  (`REPEATABLE READ`, `SERIALIZABLE`) прибрав би фантомні читання, але різко
  збільшив би кількість блокувань і ризик deadlock на `dbo.Movies` — найгарячішій
  таблиці. Там, де потрібна стабільність рядка в межах транзакції, це досягається
  точковою підказкою `UPDLOCK`, а не підняттям рівня для всієї транзакції.
- **Ідемпотентність** ключових операцій: `LateFeePayments.IdempotencyKey UNIQUE` —
  повторна відправка запиту на оплату пені не створить другий платіж.

## 8. Статуси оренди та допустимі переходи

За зразком `OrderStatus` з референсного застосунку Microsoft eShop:

```
Submitted ──► AwaitingValidation ──► DiscsConfirmed ──► PickedUp ──► Returned
    │                 │                     │
    └─────────────────┴─────────────────────┴──────► Cancelled
                                                     (лише ДО видачі дисків)
```

| Перехід | Процедура | Відмова, якщо |
|---|---|---|
| → `DiscsConfirmed` | `usp_ConfirmRentalDiscs` | статус не `Submitted`/`AwaitingValidation` → **50002**; немає позицій → 50004; не вистачає дисків → **50003** |
| → `PickedUp` | `usp_PickUpRental` | статус не `DiscsConfirmed` → **50002**; не вистачає дисків → **50003** |
| → `Returned` | `usp_ReturnRental` | статус не `PickedUp` → **50002** |
| → `Cancelled` | `usp_CancelRental` | фільми вже видані на руки → **50002** |

Коди помилок процедур перетворюються на HTTP-статуси в Лаб. 02:
**50001 → 404**, **50002 / 50003 / 50004 → 409**.
